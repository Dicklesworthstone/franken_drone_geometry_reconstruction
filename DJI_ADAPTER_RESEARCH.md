# DJI Adapter Research Program

**Status:** normative owner-authorized compatibility and adapter plan
**Default posture:** read-only, passive, exact-profile, fail-closed
**Production language/runtime:** safe Rust, asupersync, no vendor/native FFI

## 1. Mission

Build a clean-room, profile-certified Rust adapter capable of acquiring exact media, live video,
telemetry, and eventually selected camera/gimbal/assisted-flight effects from DJI systems owned and
authorized by the operator, without making FDGR's semantic architecture depend on DJI's current
SDK, application layout, transport, or cloud service.

The adapter is an effect/evidence boundary. It maps raw profile-specific behavior into stable FDGR
observations and typed operations. It does not define geometry, scale, semantic identity, or
completion.

## 2. Authorization boundary

Research and operation are limited to:

- aircraft, controllers, phones/hosts, networks, accounts, and storage controlled by the operator;
- legitimate pairing, passwords, account state, and session credentials;
- passive capture and bounded experiments explicitly enabled by a local capability;
- applicable operating/geofence/airspace and privacy constraints encoded in the profile/plan.

The project does not bypass pairing, authentication, encryption, account controls, geofencing,
firmware signature checks, or another operator's system. Secret material is held by a narrow local
capability vault and is excluded/redacted from corpora, logs, crashpacks, reports, and public
fixtures.

## 3. Exact compatibility profile

A profile identity includes:

```text
aircraft model / hardware revision
aircraft firmware and configuration
controller model / firmware / display mode
host phone/computer OS, architecture, and network interfaces
DJI application and component versions
region, radio/transmission mode, channel/band conditions
pairing/account/session mechanism
media/container/codec/profile parameters
stream transport and endpoint topology
telemetry and command grammar versions
adapter code revision and schema epoch
```

“DJI Flip” or “same major firmware” is not a profile. Unknown differences fail closed to a proven
lower capability.

## 4. Maturity ladder

| Level | Capability | Authority |
|---|---|---|
| D0 | exact original-media import from card/export | read-only evidence |
| D1 | controller/phone/display recording or capture ingest | read-only evidence |
| D2 | passive owner-network/USB stream discovery and packet recording | read-only evidence |
| D3 | authenticated live video ingest using legitimate paired state | read-only evidence |
| D4 | typed telemetry observation and clock correlation | read-only evidence |
| D5 | camera settings and recording observation/effects | bounded effect |
| D6 | gimbal observation/effects | bounded effect |
| D7 | manual next-view guidance only | no flight command |
| D8 | assisted waypoint/flight effects | high-risk fenced effect |
| D9 | autonomous mission profile | separate future approval/gate |

Each level is qualified independently. D8 does not follow automatically from discovering command
packets. D0 remains a useful product if every live surface breaks.

## 5. Research workflow

### 5.1 Establish the exact physical/software baseline

Create a private profile manifest, photograph/capture relevant settings, record versions, and seal a
known-good original media sample. Verify clocks and network interfaces. Record what the official
application/controller visibly reports.

### 5.2 Passive observation first

Capture only traffic generated by ordinary legitimate operations:

- boot and discovery;
- pairing/login/session establishment;
- idle preview;
- start/stop recording;
- camera setting changes;
- gimbal movement;
- flight-mode and telemetry changes;
- media browsing/download;
- disconnect/reconnect/shutdown.

Capture at all observable owner-controlled boundaries—host sockets, USB/network interfaces,
controller display capture, exported logs, media files—without altering protocol behavior.

### 5.3 One-variable-at-a-time experiment design

Each experiment changes one controlled variable and records:

```text
experiment ID and hypothesis
profile identity and prior state
operator action and exact timing
packet/object/host-log roots
visual/controller observation
expected versus observed differences
candidate field/state-machine interpretation
alternative explanations
confidence and next discriminating experiment
```

Examples include one camera parameter step, one gimbal axis, one recording transition, one flight
state transition, or one reconnect condition. Correlation is not promoted to causation without
discriminating experiments.

### 5.4 Build a corpus before an adapter

The corpus contains exact bytes, link-layer/transport metadata where available, bounded host logs,
screen recordings, media outputs, and experiment manifests. Sensitive fields are tagged and a
sanitized derived corpus is produced by an explicit redaction transform. Original private evidence
remains content-addressed and access-controlled.

### 5.5 Infer layered protocols

Separate:

1. discovery and endpoint selection;
2. session/authentication/key establishment;
3. liveness/heartbeat;
4. video/media channels;
5. telemetry/state;
6. camera/gimbal commands;
7. flight commands;
8. operation receipts/acknowledgments;
9. reconnect/resume/error behavior.

Do not describe an encrypted payload as “unknown command data” if the right conclusion is that the
current observation boundary cannot decode it. The design can integrate at a different legitimate
boundary.

### 5.6 Generate a state machine and grammar

A versioned owned DSL defines:

- frame/message boundaries;
- constants/tags/lengths/checksums;
- byte order and units;
- optional/conditional fields;
- sequence and replay rules;
- request/response/notification relations;
- state-machine preconditions and transitions;
- secret/redaction classes;
- malformed-input behavior;
- unknown-field preservation.

The deterministic generator emits bounded Rust parsers/encoders, human field documentation,
golden vectors, structured fuzz generators, emulator fixtures, and compatibility schemas. Generated
artifacts are checked in and drift-checked. Build time performs no network access.

## 6. Adapter process architecture

```text
fdgr-device-supervisor
├── profile-probe (read-only)
├── discovery
├── authenticated-session
│   ├── receive pump
│   ├── video lane
│   ├── telemetry lane
│   ├── effect lane
│   ├── operation lookup/reconciliation
│   └── liveness/reconnect
├── evidence normalizer
└── profile health/compatibility monitor
```

Every task is region-owned. Network/device I/O receives `&Cx` authority, deadlines, pressure, and
budgets. The profile probe cannot dispatch. The video lane cannot obtain command authority. The
effect lane cannot publish semantic geometry.

## 7. Video and media evidence

The adapter preserves:

- exact packet/media bytes;
- transport and packet sequence where observable;
- access-unit/frame boundary evidence;
- codec parameter sets and changes;
- keyframe/random-access markers;
- nominal and observed timestamps;
- crop/stabilization/display transformations;
- packet loss, duplication, reordering, truncation, and concealment status;
- relationship between live preview and original recording;
- device/app transcoding or scaling.

Live preview and high-quality original recording are separate evidence sources. They may be aligned
through clocks/content, but pixels/timestamps are never assumed equivalent. A preview-derived live
twin and original-media offline twin are successor/related generations with explicit basis.

## 8. Clock reconstruction

DJI systems may expose aircraft, camera, encoder, controller, app, host-monotonic, GPS, file, and
wall clocks. The adapter records raw values and correspondence events. Clock mapping is solved in
the authoritative evidence plane, not baked into packet parsing.

Jumps, reset, wraparound, drift-regime changes, reconnect, and recording segmentation create
explicit clock segments/epochs. A frame timestamp is never silently rewritten without retaining the
raw source and mapping generation.

## 9. Telemetry

Telemetry fields are admitted individually with:

- raw field/bytes and units;
- coordinate frame and orientation convention;
- clock domain;
- update and interpolation policy;
- validity/status flags;
- quantization and uncertainty;
- experiment/source profile;
- semantic mapping confidence;
- malformed/out-of-range behavior.

Telemetry can be a geometry/scale prior only after its own calibration and reliability gate. It is
never privileged solely because it came from the aircraft.

## 10. Effect protocol

A typed effect family defines:

```text
operation identity and canonical parameters
allowed profile states
capability and risk class
idempotency semantics
lease/fence domain
final adapter-side preconditions
dispatch encoding and bounds
transport/device acknowledgments
operation lookup/reconciliation
canonical observations
terminal predicate and tolerances
compensation or safe fallback
```

State progression distinguishes local commit, dispatch attempt, transport acceptance, device
acceptance, observed effect, and terminal proof. Connection loss can produce `Indeterminate`.
Blind retry is forbidden.

The first admitted effects SHOULD be reversible and low-risk—recording state or bounded camera/
gimbal changes—before any flight command family.

## 11. Human/manual control integration

D7 plans produce operator guidance:

- target surface/object/coverage deficit;
- recommended position region, altitude, standoff, heading, camera angle, and speed;
- visibility/occlusion explanation;
- expected information gain;
- hard no-go regions and privacy constraints;
- live completion feedback.

The operator remains the controller. Guidance is useful even without a command channel and is the
first active-perception product.

For later assisted control, human override/preemption is structural. Override closes effect
admission, drains/reconciles in-flight operations, and returns authority without orphan mission
work.

## 12. Emulator and replay

A pure-Rust deterministic emulator consumes captured fixtures and profile state machines. It can:

- replay exact packet timing under virtual time;
- inject loss/duplication/reorder/truncation;
- delay/drop acknowledgments;
- reset clocks or reconnect;
- mutate unknown fields;
- simulate command outcome before/after response loss;
- enforce rate/state-machine errors;
- model battery/link/geofence state for planning/effect tests.

The emulator is not hardware qualification. It makes every bug replayable and allows exhaustive
state/cancellation schedules before physical tests.

## 13. Compatibility promotion

A profile capability moves through:

```text
Observed
→ Hypothesized
→ ParserFixtureQualified
→ EmulatorQualified
→ PassivePhysicalQualified
→ EffectPhysicalQualified
→ Recovery/CompatibilityQualified
→ Promoted
```

Positive success evidence is mandatory. Rejection of malformed input alone is not proof the valid
path works. Promotion receipts identify exact hardware/software profile and source closure.

## 14. Degradation

On unknown profile or failure:

- preserve raw bytes and diagnostics;
- disable unproven parsing/effects;
- fall back to exact media import or a proven passive surface;
- create a new compatibility epoch;
- fence prepared plans and active command leases;
- explain the missing capability and required qualification;
- never “try the closest profile” for a command effect.

## 15. Security and privacy

- credentials live in an OS/local capability vault, never canonical project artifacts;
- packet corpora classify secrets and personal data by exact spans;
- support bundles default to sanitized fixtures and manifests;
- device serial/account/property identities can be pseudonymized;
- command rates, payload sizes, endpoints, and state transitions are bounded;
- malformed inbound frames are parsed nonrecursively with resource limits;
- untrusted strings never become paths, commands, or log format strings;
- network listening defaults to the narrow local/device interface required by the profile.

## 16. Qualification matrix

Every promoted surface covers:

- valid ordinary operation;
- malformed/truncated/oversized input;
- packet loss/reorder/duplication;
- link loss and reconnect;
- process crash/restart;
- cancellation at every yield/effect boundary;
- stale profile/epoch/lease/fence;
- operation idempotency and conflicting reuse;
- unknown outcome and reconciliation;
- pressure/backpressure and bounded memory;
- secret/redaction checks;
- exact local source-closure receipt;
- physical device success on owned equipment.

## 17. Explicit rejections

- broad ambient access to the host's DJI account or network;
- arbitrary raw command/packet tools exposed to agents;
- bypassing legitimate authentication or geofencing;
- treating one capture as proof across firmware/app versions;
- conflating preview and original pixels/timestamps;
- telemetry used as ground truth without qualification;
- ACK = terminal success;
- blind retry after connection loss;
- secrets in logs/corpora/crashpacks;
- SDK/native FFI types crossing the semantic seam;
- unknown firmware mapped to “probably compatible” command behavior;
- flight control before manual guidance, simulator, physical, fencing, and preemption gates.
